# 人間用デバッグViewer — H0設計追補

2026-09-20 / H0 v1.0 / Jev Video Context Fields 日本語設計v0.3への追加仕様

**成果物の状態：本書は実装用仕様。ユーザーPCのViewerを変更・起動した結果ではない。**

## 1. 目的・正本との関係

実際のローカル動画・音声、当時の解析結果、根拠、処理状態を同じ画面で照合し、人間が不具合・意味の不一致・判断不能を記録できるようにする。チェック結果をCodexへ渡し、修正後の人間再確認まで追跡する。自動試験の合格を、動画の意味が正しかったという判定に置き換えない。

既存の日本語設計v0.3の三つの場、来歴、因果的時刻、M3〜M5の構造を引き継ぐ。本追補は画面・記録・人間確認工程を追加するもので、Score採用契約、場の式、UNKNOWNの意味、TTL、予算を変更しない。H0はM3aの後に優先して実装し、M3b〜M5の完成やScore照会への回答を開始条件にしない。将来ASR検出・補正（会話上の仮称M6〜M8）は検査用の接続形式だけを用意し、実装済みとはしない。

## 2. 引き継ぐ実装状況と不足 [B1〜B3]

対象workspaceは報告上 `C:\dev\jev-video-context-field-po`。別の `-poc` フォルダへ作り直さない。既存のローカル動画取込み、同一bytesの再生・PTS decode、ASR原文、画像／会話解析、三つの場、根拠、UnknownTriage、既存話題readout、Replayを再利用する。HTTP＋pollingを新frameworkへ置き換えることを前提にしない。

直近比較報告では本番はC0のまま。CP／CDは比較案であり、採用されたとは扱わない。195試験・HTTP・DOM・Replayの報告はあるが、実browser操作・人間の音声／映像との意味照合の完了証拠とは異なる。報告終了時の53送信予約／56unit／148質問は参考値で、現在の予算の実値を確認して引き継ぐ。報告上はbackend・Viewer停止中だが、開始時に再確認する。

現物ソースとログschemaはCodexが読む。本書の提案API名・型名を既存APIの実在確認と誤解しない。

## 3. 最初に完成させる体験

1. ユーザーが任意の対応ローカル動画を選び、保存runを選択する。動画との一致を検査する。新しい動画だけを選んだ場合は「ログ未接続」または明示した実ローカル解析で開始する。
2. 動画を見て音声を聴き、時刻付きASR原文、画像解釈、人物・場所・会話の場を照合する。
3. 気になる項目で「この箇所を確認」を押す。対象eventと版を固定し、元発話の音声区間や対象frameを開く。
4. 「一致／一部不一致／不一致／判断不能」を付ける。期待していた内容・実際の内容・メモを保存する。未判定は未確認のまま。
5. 「Codexへ渡す確認結果を作成」で、問題一覧・再現時刻・参照ID・人間の判断・制約を保存する。
6. Codexが修正・試験し「修正済み・人間再確認待ち」とする。ユーザーが同じ問題を新build／新runで再確認して解決または再現を記録する。

特定のデモ動画、固定した話題、決まった時刻の正解に依存させない。1本目から実ファイルで使える画面を優先する。

## 4. 画面構成

既存の左動画・右三つの場を基礎に、デバッグモードを加える。新しい独立した合成ダッシュボードを作って既存実装との接続を後回しにしない。

| 領域 | 内容と操作 |
|---|---|

| 左上：実動画・音声 | 再生／停止、音量、対象区間反復、レビュー専用速度変更、前後の実frame、元frameと解析cropの切替。 |
| 左下：会話原文 | ASR原文、発話ID・版・時刻、クリックで音声区間を聴く。人間の参照文／将来の補正案とは別欄。 |
| 右上：場・readout | 人物・場所・会話。濃度、UNKNOWN、支持／反証、Jevの読取りを区別。全人物・全facet・OTHER内部を一覧で選べる。 |
| 右下：根拠・処理 | 元観測→候補→Evidence→寄与→snapshot→Dominance→readoutを、実在する参照で追う。失敗段階も表示。 |
| 下部：時間軸 | 公開範囲、ASR実入力区間、認識segment、未解析／不明区間、frame／cut、評価到着、停止・失効、チェック済み区間。 |
| 確認パネル | 判定、問題種別、重要度、期待／実際、自由記述、次へ、保存、再確認状態。常時全詳細を展開しない。 |

16px前後を基本に可読性を確保し、色だけに頼らず状態名を併記する。狭い表示幅では縦に積み、原動画と原文を読める大きさを優先。主要操作はキーボード対応し、入力欄内のキーで動画操作を誤発火させない。ユーザーの端末サイズは実browserで確認し固定値に依存しない。

## 5. モードと副作用を分ける

### 5.1 モード一覧

| モード | 観測・評価 | 許される書込み・送信 |
|---|---|---|
| `REPLAY_EXACT` | 保存された当時の結果と同じ動画 | 新推論・Jev予約・キー読取りなし。人間注釈だけ別ファイルへ保存。 |
| `MEDIA_ONLY_REVIEW` | 動画のみ。出力未接続を明示 | 人間による区間メモ。モデル出力を捏造しない。 |
| `LOCAL_REAL_EVAL_MOCK` | 実動画と実ローカルモデル、評価のみMOCK | 明示開始後に新local run。Jev送信・実キーなし。MOCK由来の意味品質を実Jevへ一般化しない。 |
| `LIVE_JEV` | 許可済み実動画・実Jev | 既存認可・実予算・現行policyを使い明示開始した場合だけ。通常LIVEの未解決条件を表示。 |
| `STATIC_POLICY_COMPARE` | 同じ保存応答へCP／CD等を適用した別の試算 | 新規送信・場への書戻しなし。旧runで実表示された結果としない。 |

観測の由来（実／合成）、評価の由来（実Jev／MOCK／なし）、表示モード（Replay／LIVE／静的比較）は別フィールド。単に「LIVE」一語で実観測と実評価を混ぜない。

### 5.2 H0の初回実装・確認の範囲

初回はReplay／動画単独レビューを既定とし、利用者が明示して実ローカル解析＋MOCK評価を使えるようにする。今回のCodex実装作業では新規Jev送信・実予算予約・実キー読取りを行わない。既存のLIVE承認を撤回するわけではなく、過去の原本取得case_02／03を再開する指示でもない。

新しいdebug起動は、実transport・LiveCapability・実予算writerを作らない。閲覧にcampaign排他を長時間占有させない。statusのための読み取りで予約を生じさせない。通常LIVEは明示操作・その時点の作業範囲に従う別経路で、画面を開く・保存runを選ぶだけで起動しない。

### 5.3 GETを診断処理の起動にしない

既存報告では `/api/snapshot` の内部で `collect()`／`view()` が動く経路がある。debug/replayの読み取りはそれを無条件に再利用しない。固定cursorのread-only accessorを作り、GET・polling・原文クリック・フレーム表示・注釈保存で、新規推論・送信・再評価・場更新が起きないことを試験する。

同一backendに置く場合も、read-only review serviceとlive serviceの依存を分ける。UI状態と実行状態を混ぜず、2ブラウザータブの古い操作から別runを変更しない。

## 6. 動画とログ・時刻の対応

### 6.1 同じ動画であること

ユーザーが選択したfileを既存の取込み経路でbackend管理assetへ登録し、可能なら保存runのmedia hash・byte_sizeと照合する。同名だけで一致としない。ファイル選択から本当の元絶対pathが得られない場合はnullとし、backendコピーの実在pathをprivateに保持する。fakepathやモデル出力中のpathを資産参照にしない。

hashが旧ログにない場合は、手動対応付けと検証済みを区別し、`media_match=unverified`とする。一致を確認できない場合はその動画で旧結果を採点したと報告しない。明示的な動画単独メモは可能にする。既存の取込み容量・対応codec制限は勝手に広げない。

長尺の対応動画を開くことは可能にするが、新しい解析は既存の最大120秒区間を維持。初回チェックは30〜60秒の区間を提案し、結果に都合のよい区間だけを成功例として選ばない。

### 6.2 三つの時刻とcursor

常に次を区別する。
- **レビュー再生位置**：人間がいま見ている動画の時刻。
- **出典／入力の時刻**：ASRや画像解析、readoutが実際に参照した時刻または区間。
- **当時の表示時刻・event cursor**：その結果が利用可能になり、表示された時点。

同じmedia時刻でもpause中の遅着・ASR改訂・同地点へのseekで状態が違う。Replayの正式な選択キーはrun＋epoch＋event cursorであり、video秒だけにしない。動画秒から検索するときは、該当するepochと利用可能状態を選ばせ、曖昧な場合に最終版を黙って選ばない。

再生位置59秒に対してreadout入力28.7秒なら両方を表示し、ラベルの意味は元根拠で、遅延は表示時刻との差で別に確認する。証拠へ移動するとレビューplayerだけを動かし、現在の解析時計・epochをseekしない。

### 6.3 フレームと音声

元の整数PTS／time_base／開始offsetと実使用streamを使う。目的時刻付近へseek後、decodeを進めて対象frameを取る。要求時刻に完全一致するPTSがなければ、表示区間対応・直前等の一致種別と実際のPTSを示す。「フレーム送り」は名目fpsから1/fpsを足す方法で正確と呼ばず、実decodeした隣接frameを使う。

原frame、VLMへ渡した縮小・crop・rotation、匿名track領域を区別する。解析器入力の画素が保存されていなければ、元動画からの再構成画像であることを表示し、同一入力と断定しない。

ASR区間反復はsample時刻を使い、単語時刻がない場合は発話区間単位とする。短い前後文脈を追加再生した場合は対象区間と追加区間を区別する。聴き取れない場合は参照文を強制入力させない。再生したことが理解した証明ではなく、人間が見た／聴いた／未確認を明示して保存する。

### 6.4 LIVE中の確認

「この箇所を確認」は対象の不変スナップショットとIDを先に固定し、必要なら正規のpauseを要求する。通常pauseで処理中の妥当な結果が後着しても、編集中の対象を自動置換しない。LIVEの入力を一時停止する操作と、検査欄だけ固定する操作は表示を分ける。

独立したレビューplayerの反復、コマ送り、0.5倍速等をlive時計の公開通知へ接続しない。LIVEで未対応の速度は無効化する。レビューで後続場面を見た場合の知識露出は注釈に記録する。

## 8. Score問題を観察可能にする（採用変更ではない）

C0を現行と表示し、現在のreadout error/nullと停止原因を保持する。診断欄では受信済みscore、確率分布、独立期待値、差、検証結果、policy版、原本の証拠段階（完全body／再serialize／欠損）を表示できる。

CP／CDの計算候補を出す場合は、静的比較の独立欄に「未適用・仮定の値」と常時表示する。従来C0で棄却されたreadoutを、主表示のvalidへ昇格させない。case_01は合成の原本診断でFieldSnapshotがないため、任意の実動画のある時刻へ関連付けない。

人間は数値不一致の有無と意味内容の妥当性を別々に記録する。「意味は妥当」にチェックしても、validatorを迂回して採用・送信再開しない。今回の実装でC0／CP／CD切替による本番採用機能や全体停止の緩和は追加しない。

Score不良が残っていても、受信済み候補・原文・画像記述・正常unit・停止原因を検査可能にする。元ログに存在しない、停止後に送ったはずの応答を作らない。

## 9. 人間チェックのデータと状態

### 9.1 四つの確認を別にする

- `numeric_status`：数値・schema検査。自動検算結果の由来と版を保持。
- `pipeline_status`：配線・時刻・依存版・表示処理の確認。
- `semantic_verdict`：人間の、元資料に対する意味判断。
- `review_status`：未確認／途中／保存済み。機能の実装状態とは別。

意味判定は `consistent_with_evidence / partially_inconsistent / contradicted_by_evidence / ambiguous / not_assessable / unreviewed`。複数主張が混ざった項目はsubclaimへ分ける。人間には「濃度の正解小数」を強制しない。段階評価を付ける場合だけ対象の同じrubricを提示する。

`expected_text`等の人間参照はASR原文・モデル出力とは別。1人の判断を自動的に普遍的正解や学習ラベルとしない。人間同士／Codexと意見が分かれたら別annotationとして保持する。

### 9.2 対象の固定と保存

`HumanReviewRecord`はreview ID、reviewer、target ID、run、epoch、event cursor、対象ID／版、source範囲、asset hash、build／policy／registry版、判定、メモ、実際に確認した入力、保存時刻を持つ。クリック後に後着ASR版へ対象を取り替えない。データ不足はnull＋理由で保持する。

人間の編集は新revisionとして保存し、前の判定を削除しない。保存要求にはidempotency keyと期待revisionを使い、再送による二重登録と複数tabでの上書きを防ぐ。backend永続保存のACK後だけ「保存済み」と表示する。localStorageだけを正式保存先としない。

AIの提案は `author_kind=assistant_proposal` 等の別種にする。Codexや通常テストが本物の人間確認を登録したり、人間チェックを勝手に完了にしない。認証を追加しないローカル単一ユーザー方式ではreviewer名は自己申告であり、身元保証ではない。

### 9.3 見た情報と先入観の記録

診断用途ではモデル結果を見ながら照合してよい。品質比較用には「原動画・音声を先に確認→人間の参照を保存→モデル結果を開く」という任意の順を用意する。

`model_output_exposure`、`future_content_exposure`、`review_basis`を記録する。人間は後続内容を忘れられないので、表示を隠しただけで厳密as-ofや独立盲検に戻ったとしない。対象時点以前の未入力frameを再取得した場合も、当時の入力そのものと区別する。

### 9.4 不具合のライフサイクル

`open → triaged → fixed_pending_human → verified_by_human` を基本に、再現時は `reopened`、対応しない判断は理由付き `deferred`。Codexが修正と自動試験を終えた状態は `fixed_pending_human`。意味・画面操作の人間確認を自動で代行して閉じない。

旧runの問題はそのまま残し、修正build・新run・同じ再現操作と、新しいHumanReviewRecordを参照して解決を記録する。review完了や高評価でfieldを書き換えない。

## 10. チェック工程とリリース判断

Codexは許可範囲で実装→自動試験→修正→デモ準備をまとめる。各file・各応答ごとに人間へ確認を求めない。動くbuildと短いチェックリストが揃ってから、人間が一括して確認する。

機能ごとに「実装」「自動試験」「実素材接続」「人間操作確認」「意味確認」を別欄で提示する。UNKNOWN保持・人物なし・API棄却等で意味確認不能な項目は、合格でなく理由付き未確認／非該当。基準build・素材hash・確認範囲が変わったら、影響するチェックだけ再確認対象にする。

初回の機能確認は短い実素材と代表的な正常・異常区間で行う。確認した区間・対象数と未確認範囲を記録し、「全動画・全内容が正しい」としない。すべての対象を人間が毎tick確認する運用は要求しない。全場一覧を提供することと、全件の意味検証を完了することを区別する。

少なくとも、当該buildで必須とした操作チェック、実素材との一致確認、注釈の永続化・export・再確認を終えるまでは `human_acceptance=pending` と表示する。未確認の機能を「受入れ済み」としないが、独立した開発や安全なReplay閲覧を全停止する条件にはしない。

品質評価の母数には実際に人間が判定できた範囲を用い、サンプル抽出・曖昧・非該当・未実装を別集計する。本人が付けた結果との一致率を、一般的な精度と呼ばない。

```text
human-review/<review_id>/
  manifest.json                 # 対象run・動画hash・build・各版・範囲
  checks.json                   # 必須/将来機能、状態、人間確認の参照
  annotations.jsonl             # 人間判定の全revision
  issues.jsonl                  # 修正依頼・再確認状態
  private/media-links.json      # allowlist対象の実在媒体参照
  export/codex-feedback.md      # 人間用の要約・再現手順
  export/findings.jsonl         # 構造化した確認結果
```

run原本・生HTTP本文・過去のfield snapshotは読取り専用。annotation・索引は別に保存する。旧ログにないPTS・原文版・raw bodyを復元したことにしない。

Codex渡しには問題の再現時刻／cursor、対象ID、期待／実際、使用build、元資料参照、重要度、未確認情報を含める。既存workspaceの許可媒体をローカルで再確認するためのprivate情報は共有exportと分離する。元動画・音声・画像・絶対path・秘密・全run・raw bodyを自動で外部へuploadしない。CSV等を追加する場合は数式注入対策、HTMLは常にtextとして扱う。

「Codexへ渡す」はまずファイルを生成して保存場所を案内する実装でよい。既存セッションへ送れた／自動で修正が始まったと表示しない。将来の起動adapterが接続済みならその実状態を表示し、ログやメモからshell命令を実行しない。

人間参照文・注釈はJev入力・カテゴリ発見・ASR補正の学習／推論へ自動投入しない。別の許可された開発レビューで参照し、次runの版付き修正に使う。検証に使った動画を新定義の独立評価データとは呼ばない。

## 12. 性能・安全・後方互換

既存報告に大きなJSONL runがあるため、ログはstream読取りと派生索引、ページングで扱う。ブラウザーへ全runを一括送信しない。検索・フィルタ・前後event・対象frame取得は必要範囲に限定する。遅い取得はprogress・cancelを持ち、キャンセルで元runを破損させない。数百MBログをfixtureだけで軽いと判断しない。

localhost、Origin、session token、media allowlist、入力サイズの境界を維持する。読み取り元は選択したrun／媒体と管理下artifactのみ。パス探索、`.env`読み、ネットワーク共有の自動マウント、URLからの動画取得を行わない。HTML/JSを含む原文・OCR・メモもコード実行しない。

`.env`、cookie、認証headerやtokenを画面・export・hash対象にしない。レビュー画面からprivate raw archive全体を公開しない。必要な値だけを認証された検査APIで取り出す。

## 13. 拡張interface

`DebugFeatureAdapter`の提案契約は次とする。実ファイル名は現行構成へ合わせる。

- capability：`implemented / planned / disabled / unavailable`と根拠となるbuild・設定。
- list_targets：run＋cursor＋範囲から検査対象をページング列挙。表示されなかった対象も扱う。
- get_target：対象の不変payload・依存版・来歴・欠損理由を返す。
- get_evidence：認可された媒体／原文参照を返す。新しいモデル推論を起動しない。
- review_schema：入力可能な人間判定、参照文、機能固有の補助項目。
- export_reference：問題を再現するための安全な参照。

H0では既存機能adapterを実接続し、M3b以降はplannedとして列挙する。未来のadapterが返す想定データを本物と混ぜない。同梱JSON schemaはレビュー保存形式の出発点で、媒体参照・版・時刻・権限等の意味検証は通常コードで追加する。

## 14. 実装順序

**H0a：最初の人間確認。** 実動画＋保存run、原文／frame、原文・場への参照、判定保存、Codex向けexportを縦につなぐ。

**H0b：原因と時刻を追う。** 全場・全対象、処理時間軸、ASR input coverage、Jev不一致検査、二重時刻／cursor、旧ログ欠損、read-only境界を完成させる。

**H0c：今後も使える確認工程。** 機能能力一覧、必須チェックと未確認表示、修正後再確認、将来adapter、回帰とデモ準備を完了する。

三段を同じ許可範囲で継続し、段階ごとの細かな承認で止めない。M4の全自動レビューやM6のASR補正を完成させないとH0が使えない構成にはしない。
